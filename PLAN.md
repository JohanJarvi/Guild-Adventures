# Guild Adventures - Roadmap

Living planning document for where this app is headed. Update it as enhancements land or the design changes - treat it like [diagrams/node-graph.md](diagrams/node-graph.md), not a one-off spec.

Four enhancements, meant to be built roughly in this order - each one is a reasonable foundation for the next:

1. **Life system** - dying isn't instant game over.
2. **Flavor beats** - every option click passes through a witty moment before landing.
3. **Voiceover + pacing** - the flavor/terminal screens narrate themselves and auto-advance.
4. **Multiplayer via WebSockets** - a room full of people vote on the same playthrough.

---

## 1. Life system

**Goal:** three lives before a real game over. Dying with lives remaining just costs a life and restarts the story - it does **not** wipe out previously eliminated options.

**Current behavior to build on:** `app/AdventureGame.tsx`'s `nodes` state (the elimination map) already never resets on its own - reaching death today already preserves prior choices, purely by accident of there being no reset code at all. That part needs no change.

**What's actually new:**
- A `livesRemaining` piece of state in `AdventureGame.tsx`, starting at 3.
- Decrement it whenever the player reaches the death node (999).
- **While `livesRemaining > 0`:** skip the existing "Game Over! Try again?" framing entirely (node 9999) - it reads wrong when you're not actually out. Route straight from death back to node 0, keep the elimination map exactly as it is, just show the player their remaining lives somewhere on screen.
- **When `livesRemaining` hits 0:** this is the real game over. Show a distinct message (node 9999's current text becomes the "true end" state), and on retry: reset the `nodes` elimination map back to pristine *and* reset `livesRemaining` back to 3.

**Design decision to make when implementing:** node 9999's displayed text needs to vary by lives remaining ("You died. 2 lives left." vs. the real "Game Over! Try again?"). That's session state, not story content, so it should live in `AdventureGame.tsx` as a small conditional rather than becoming new entries in `data/nodes.ts` - the graph data stays about the *story*, not about session bookkeeping.

**Scope:** entirely client-side, no new dependencies, no backend. Smallest of the four.

## 2. Flavor beats between every option and its destination

**Goal:** no option should jump straight from one "hub" (a node with real choices, like `Smile!`) to another hub with zero reaction in between. Every option click should land on a short, witty, no-option node first - the same pattern already used to fix the `node7/13`, `node17/18`, and `node23/24` stuck-loop bugs - before either looping back to a hub or progressing onward.

**This is content work, not new application code.** The existing `notice.nextNode` chaining already fully supports it (that's exactly how the alien-denial and wall-licking chains work today). The job is adding more no-option "flavor" nodes to `data/nodes.ts`, not building new mechanics.

| node4 | "Lie down and try not to cry" | node8 |
| node6 | "Crawl... north?" | node7 |

**Suggested tooling:** add a non-blocking check (a script, not a hard throw in `getNodes()` - this is a style guideline, not a correctness bug) that flags any new hub-to-hub edge without a flavor node in between, so this checklist doesn't silently reappear as the graph grows. Model it on the cycle-detection script already used to find the stuck-loop bugs.

## 3. Voiceover and pacing

**Goal:** the text in the center of the screen narrates itself. On any no-option screen, once narration finishes, wait an additional 5 seconds, then auto-advance exactly as if the player had clicked the title.

**Depends on (2):** the more flavor nodes exist, the more the game benefits from auto-advancing through them instead of requiring a click every time - build this after there's real content to narrate.

**Key decision: pre-generate audio, don't synthesize live.** The story text in `data/nodes.ts` is static content, not user input, so there's no reason to call a TTS API at runtime:
- **Recommended:** generate an audio file per node's `notice.value` once (as a content-authoring/build step), store it as a static asset (e.g. `public/audio/{nodeKey}.mp3`), and just play it back client-side. Zero runtime API cost, zero latency, works offline, no backend or secrets needed.
- **Alternative (simplest to prototype, lower quality):** the browser's built-in `SpeechSynthesis` Web Speech API - free and needs no backend, but voice quality and availability vary a lot across browsers/OSes, and it can't be pre-rendered.
- Either way this is additive to the existing static/SSR architecture - it doesn't require enhancement 4's backend.

**Mechanics:**
- On mount of a no-option node, play its narration.
- On the audio's `ended` event (native `<audio>` element if pre-generated, or `SpeechSynthesisUtterance.onend` for Web Speech), start a 5s timer.
- On timer end, trigger the same navigation the header click already does (`notice.nextNode`).
- Nodes *with* options should not auto-advance - narration can still play, but the player picks.

**Open questions to settle before building:**
- Browsers block audio autoplay without a prior user gesture - probably need a "click to start" gate on first load rather than autoplaying immediately.
- Should the timer be skippable (click anywhere to jump ahead) for replayability, or is the pacing part of the joke? Worth a call before implementing, not a technical blocker either way.
- Mute toggle - almost certainly wanted, cheap to add.

## 4. Multiplayer via WebSockets

**Goal:** host a session, others join, everyone votes on the current option, a visible countdown runs, the option with the most votes wins when it expires.

**This is the big one - a real architecture change**, not an incremental add like 1-3. Worth its own focused design pass (e.g. a dedicated planning session) when it's actually time to build it; what follows are the decisions that shape everything else, not a full spec.

**From client-authoritative to server-authoritative state.** Today, `AdventureGame.tsx` computes everything locally (`shownNode`, the elimination map, and - after enhancement 1 - lives). For multiplayer, a shared session needs one source of truth:
- The **server** holds, per session/room: current node, the elimination map, lives remaining, connected players, and the live vote tally for the pending decision.
- **Clients** become thin: render whatever the server broadcasts, and send "I vote for option X" instead of calling `setShownNode` directly.
- This is a genuine rewrite of `AdventureGame.tsx`'s responsibilities, not an extension of it.

**Transport decision (needs to be made based on hosting target):**
- Next.js on typical serverless/edge hosting (e.g. Vercel's default deployment model) doesn't support long-lived WebSocket connections in serverless functions - this is a hard constraint, not a preference.
- **Option A - managed realtime service** (Pusher, Ably, Supabase Realtime, PartyKit, etc.): the app publishes events via a Next.js API route/Server Action, clients subscribe through the provider's SDK. No custom server to run or host; fastest to stand up.
- **Option B - a standalone WebSocket server** (Node + `ws`/`socket.io`) running as its own persistent process, deployed somewhere that supports long-running processes (Fly.io, Railway, a VPS, etc.) rather than Vercel-style serverless. More control, more infrastructure to own.
- Recommendation for a hobby project: start with Option A unless there's a specific reason to self-host the realtime layer.

**Session/room model needed:**
- A room code or session ID and URL scheme (e.g. `/session/[roomId]`).
- Create-session (host) and join-session (enter code) flows - basic lobby UX that doesn't exist today at all.
- Server-side countdown timer, so all clients see the *same* countdown rather than independently-computed ones that could drift.

**Majority-vote resolution:**
- Tally votes when the countdown ends; the option with the most votes is chosen.
- **Open question:** tie-breaking rule isn't specified yet - random among the tied leaders? First option numerically? Host breaks ties? Needs a decision before implementation.

**Persistence:** in-memory session state on the server is a reasonable v1 (sessions lost on server restart/redeploy) - a database/Redis layer for durable sessions is a future-future concern, not needed to ship this.

**Interaction with enhancements 1-3:** elimination map and lives become *session* state (shared across everyone in the room) instead of per-browser state. Voiceover/timing (3) likely needs to be server-paced too, for the same reason the vote countdown does - so all clients stay in sync.
